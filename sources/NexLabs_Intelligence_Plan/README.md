# NexLabs Intelligence & Memory System
**NLE-INT-PLAN-001 | v0.1.0-proposed | 2026-11-26 | SPECIFIED_NOT_QUALIFIED**

Proposta de arquitetura, não implementação. Nenhuma alteração no GitHub, Paperclip, contas, infraestrutura ou credenciais; nenhum gasto novo. Fontes de entrada locais: catálogo 105 agentes, registry 92 pacotes/1.110 atribuições e 62 workflows. Consulte `source-lock.json`, `agent-memory-bindings.json`, `workflow-memory-bindings.json`, `skill-learning-bindings.json`, `benchmarks.json` e `contracts.json`. Os vínculos são propostas de finalidade, não grants. A ratificação do proprietário e o Source Pack do projeto precedem execução.

## 1. Objetivo e escopo
NECESSARY: recuperação fundamentada, memória isolada, proveniência, grafo temporal, feedback sem autoedição, avaliação, orçamento, revogação, recuperação, evidências. IMPORTANT: reranker local, compressão semântica, grafo avançado se comprovada vantagem. FUTURE: fine-tuning offline com dados autorizados, graph DB separado, modelos maiores; nenhum deles necessário para v1. OUT OF SCOPE: treinamento autônomo, alteração de políticas/identidade pelo executor, dados reais no piloto, novas assinaturas, ordens financeiras reais, efeitos externos não aprovados, scraping não autorizado.

## 2. Source Hierarchy e confiança
Hierarquia de engenharia preservada: checkpoint > Decisions Ledger/ADR > Scope > DoD > Architecture > Requirements > demais fontes; Git, código, testes e evidências prevalecem sobre lembranças e resumos. Para fatos não técnicos usar sistema de registro autorizado (CRM, financeiro, métricas oficiais), fonte primária datada, fontes secundárias, memória validada. Separar autoridade para ações de autoridade factual: nenhuma fonte recuperada pode conceder permissão. Conflitos não são resolvidos por popularidade ou score vetorial; reportar versões, escalar ao responsável. Não indexar credenciais, secrets, chaves privadas, prompts internos privilegiados ou dados cuja finalidade/base de tratamento não foi aprovada. Git guarda políticas, schema, hashes e referências, não dados privados. Documentos de clientes ficam em storage privado. Dado simulado é rotulado de ponta a ponta.

## 3. Arquitetura
Paperclip continua control plane (tarefas, identidade, sessões, orçamentos, skills). Knowledge Gateway independente valida identidade e task lease emitido pelo serviço de autorização; a identidade declarada no payload não é confiável. Gateway é único acesso de agentes ao conteúdo corporativo; usa roles DB sem owner/superuser/BYPASSRLS. Pipeline de ingestão, retrieval, graph, memory, feedback, eval, context e audit são componentes lógicos, inicialmente um serviço modular + worker de fila persistente. PostgreSQL dedicado logicamente ao Intelligence Hub; nenhuma edição direta do schema interno do Paperclip. pgvector + full text search; relações em tabelas SQL, sem banco de grafo dedicado inicialmente. Storage privado criptografado para documentos/artefatos, backups e evidências com metadados mínimos. Git para policies/skills versionadas e assinadas/verificadas. Gateway interno HTTP, adaptador MCP opcional com as mesmas autorizações; não expor diretamente à internet. Reutilizar componentes nativos após preflight de versão/adapter, sem copiar recursos já adequados.

Fluxo: Paperclip task -> lease -> policy decision -> contexto canônico -> retrieval ACL -> fontes + grafo -> budget -> executor -> claims + citations -> validator -> output -> candidate feedback -> independent review -> versioned release. Policy/enforcement fica fora do modelo. Rede e filesystem restritos; agents não têm Docker socket, DB admin, acesso ao Git protegido, storage bruto nem credenciais permanentes. Desabilitar/neutralizar edit tools, auto-sync e instruções da skill PARA que promovam alterações críticas; validar runtime, não só prompt. Caso adaptador não respeite fronteiras, BLOCKED.

## 4. Memória
| Camada | Conteúdo | Escopo | Escrita |
|---|---|---|---|
| M0 working | contexto da execução, task state | task + agent + tenant | TTL, descartável |
| M1 episodic | resultado, evidência, erro, handoff | projeto/cliente/agente | append via gateway, status observado |
| M2 semantic | fatos e lições aprovados, referências | corp/departamento/projeto/cliente | proposta por agente; promoção por revisor autorizado |
| M3 procedural | skills, playbooks, instruções operacionais | pacote/versão e bindings | Git PR, testes, auditoria e release |
| M4 canonical | checkpoint, ADR, políticas, contratos | escopo explícito | fonte de verdade, sem escrita por memória |
| M5 external | notícias, documentação, preços e dados de mercado | público ou licença/tenant | ingestão em quarentena, validade e as_of |

Estados: OBSERVED -> CANDIDATE -> QUARANTINED/REVIEWED -> APPROVED -> ACTIVE -> SUPERSEDED/EXPIRED/REVOKED. Transições autorizadas e auditadas, sem autoaprovação. Observações não contam como fatos. Memória individual nunca concede acesso a outro projeto. Relatórios corporativos transversais apenas agregados/minimizados e autorizados; nenhuma herança automática por hierarquia. Sessões Paperclip e workspaces por (tenant,project,agent,policy epoch); revogação encerra leases e sessões, elimina caches e exige novo contexto. Identidade e políticas são montadas somente leitura ou validadas por digest em toda execução; cópias locais modificadas não são fontes aceitas.

Retenção proposta para piloto sintético: working 24h, observações 30d, drafts 30d, cache até 15 min ou TTL menor, logs sanitizados 90d, conhecimento aprovado enquanto válido com revisão periódica. Para produção: matriz de finalidade/base legal/contratos, TTL por categoria, legal hold específico, revisão ARGUS e proprietário. Exclusão autorizada propaga a documentos/chunks/embeddings/edges/summaries/cache/exports e índices; tombstone impede ressurreição por restore. Backups com janela de retenção aprovada; restore em quarentena aplica tombstones antes de servir. Logs preservam eventos mínimos sem conteúdo removido. Atender direitos de titulares conforme aplicável; LGPD não se resume a TTL.

## 5. RAG híbrido e prevenção de alucinações
1) Intake: source allowlist, MIME/tamanho, parser sem execução de macros/scripts, scan de secrets/malware, licenças, minimização, tenant/projeto/ACL, checksum e registro de versão; quarentena se falhar.
2) Chunk por heading/função/seção, preservar offset/linha/página, source/version/as_of; candidato inicial 350–650 tokens, 50–80 overlap em prosa, código/contratos por estrutura e sem splitting cego. Embeddings com revisão pinada, dimensão e versão do pipeline; modelo local multilíngue e5-small (384 dimensões, MIT conforme model card), CPU como candidato; validar PT-BR/EN e ARM64. Não misturar espaços vetoriais; reindexação blue-green e rollback.
3) Query: intent, escopo e validade resolvidos pelo gateway. ACL/filtros antes da exposição ao modelo, DB RLS + role/grants. Consultas lexical (FTS/exact identifiers) e vetorial em escopo autorizado; inicialmente exact search, HNSW apenas se benchmark provar ganho e recall sob filtros. Fusão RRF; dedup por versão e conteúdo; top 20 de cada canal e 4–8 trechos finais como hipótese, com cap de tokens. Rerank local opcional. Graph expansion 1–2 hops, cap 50 nós, caminhos ACL-safe; sem ampliar lease. Ingest/retrieval caches tenant-scoped e policy-aware.
4) Context Pack: tarefa, critérios, políticas imutáveis, source hierarchy, hashes, evidências selecionadas, lacunas, conflitos, budget, expiry. Conteúdo externo delimitado como dados não confiáveis. Nunca executar instrução encontrada em documento. Separar parser de ferramenta; policy verifica ação/args/effects após geração; validar saída.
5) Answer contract: cada afirmação material tem source_id, version, locator e as_of; separar FATO/INFERÊNCIA/HIPÓTESE/SEM_EVIDÊNCIA/CONFLITO. Confirmação com fonte primária quando necessária; duas fontes independentes quando pertinente, sem contar republicação como independente. Não usar autoconfiança do LLM como prova. Citações precisam existir, estar autorizadas, atuais e sustentar a afirmação; validação determinística + revisão amostral semântica. Cálculos com SQL/Python e unidades; testes de engenharia via código/CI; financeiro via dados datados e reconciliação. Sem fonte válida: abster, solicitar dado ou BLOCKED. Fluxos críticos sem evidência completa não avançam. Nenhuma promessa de zero alucinação: medir, detectar e conter.

## 6. Knowledge Graph
Nós: Organization, Department, Agent, Client, Project, Repository, WorkOrder, Decision, Requirement, SkillPackage, SkillVersion, Workflow, Run, Evidence, SourceVersion, Claim, Product, Campaign, Lead, MetricObservation, Incident, Lesson, Evaluation, Release. Arestas tipadas: REPORTS_TO, USES, REQUIRES, IMPLEMENTS, VERIFIES, DERIVED_FROM, SUPERSEDES, CONTRADICTS, BELONGS_TO, PRODUCED, AFFECTS, MEASURED_BY, EVALUATED_BY, APPROVED_BY. Arestas contêm tenant/scope, evidence_id, valid_from/valid_to, observed_at, status, confidence rubric e ACL. Fatos candidatos não participam do grafo factual ativo. Relação entre cliente e campanha não libera leitura do cliente. IDs estáveis e chaves de entidade específicas do escopo; desambiguar homônimos; merges aprovados e reversíveis. Exemplo: WO -> IMPLEMENTS -> Requirement; PR Evidence -> VERIFIES -> Requirement; Lesson -> DERIVED_FROM -> Incident; SkillVersion -> EVALUATED_BY -> Evaluation. Usar CTE recursiva com limite de profundidade, visited-set e timeout; monitorar expansão. GraphRAG é opt-in após comparação com RAG híbrido, não requisito de serviço externo.

## 7. Aprendizado contínuo controlado
Triggers: run finalizado, correção, incidente, feedback do proprietário, revisão editorial, divergência factual, release, mudança de documentação, benchmark regressivo. Capturar evento estruturado com outcome, fontes, contexto mínimo, versão skill/modelo, custo e impacto; não registrar raciocínio privado nem sessão bruta. Agente propõe LessonCandidate (problema, causa observada/hipótese, correção, evidência, aplicabilidade, riscos e escopo); dedup pelo conteúdo e escopo. Knowledge Manager revisa fatos, especialista valida domínio, ARGUS valida segurança e privacidade. Se for lição factual sem mudar comportamento crítico, promover pela política de aprovação segregada; se skill, abrir PR com delta, AC, rollback e testes. Autor não aprova o próprio delta. Reviewer independente e gate humano para alterações de instruções críticas, permissões, limites, políticas, budget, modelos não qualificados, publicação e finanças. Mesmo ZEUS não possui bypass. Learning Engine não possui credencial de merge/release ou alteração de grants. Deploy de skill não amplia ferramentas; binding e policy epoch verificados. Alterações de policy somente via processo administrativo separado.

Ciclo skill: BASELINE -> CANDIDATE -> OFFLINE_EVAL -> SECURITY_REVIEW -> SHADOW -> CANARY -> APPROVED_RELEASE -> MONITOR -> ROLLBACK/SUSPENDED. Shadow/canary em fixtures sintéticas, sem efeitos externos, comparação com baseline e holdout. Promoção explícita por serviço de release segregado após aprovação; pin version+digest por agent/run. Atualizações externas entram em quarentena, não latest automático. Rollback para última versão comprovada e invalidar caches/leases/contextos dependentes. Reavaliar feedback com resultados reais só após autorização e dados suficientes; não aprender por likes isolados ou um trade vencedor. Não usar dados de clientes para treino/modelos compartilhados sem consentimento/base aplicável, avaliação jurídica e autorização específica. Fine-tuning não faz parte do v1.

## 8. Isolamento e threat model
Escopos PUBLIC, CORP, DEPARTMENT, PROJECT, CLIENT, AGENT_PRIVATE, RESTRICTED. Deny by default. Scope membership + purpose + task lease + classificação + action allowlist + policy epoch + provider approval. Grants não inferidos de departamento, cargo, grafo, skills ou prompt. RLS FORCED nas tabelas de conteúdo, tenancy em chaves e foreign keys compostas, DB role não owner e sem BYPASSRLS, transação com identidade verificada por gateway, reset pool e teste de contexto residual; não aceitar tenant do modelo. ACL na leitura/escrita de cada objeto, fonte, chunk, edge, cache, export e storage; chave cache contém tenant, project, principal/grant digest, policy epoch, corpus/version, model e prompt; nunca compartilhar contexto privado. Workspaces e sessões separados por tenant, credenciais efêmeras por tarefa, sandbox sem mounts de outro cliente, saída restrita. Providers externos: preflight de termos, retenção, localização/transferência, autorização do cliente, quota e custos; se não autorizado, execução local/sanitização permitida ou BLOCKED, nunca fallback automático. Restrito não vai a provedor não aprovado; sem endpoints de execução real de trading. Prompt injection e RAG poisoning tratados como dados hostis, com quarantine, least privilege, validação de tool args, allowlist e saída, aprovação humana onde necessário. Teste de exfil via citação/URL, contagem, graph paths, erro, logs, cache, embeddings e backup. Sem credenciais em benchmark. Auditoria append-only com hash chain e âncora independente; não alegar inviolabilidade contra administrador. Redigir conteúdos sensíveis e aplicar retenção.

## 9. Context e economia de tokens
Stable prefix: identidade/guardrails e tool schemas versionados; depois delta task, decisões e evidência sob demanda. Context Lock combina base/head Git, checkpoint/ADR/Scope/DoD, skill release, corpus epoch, policy epoch, model/adapter, source ids/hashes. Mudança relevante -> STALE, invalidar e recompilar antes de continuar. Não resumir regras críticas, valores contratuais, unidades, source pointers ou critérios de aceite; resumo ligado à fonte, nunca autoridade independente. Cache determinístico local para parsing, embeddings, cálculos e retrieval autorizados. Prompt caching só quando executor/provedor oferece telemetria e política de retenção compatível; não pressupor cache API no Plus. Budgets iniciais por tarefa (input/output; hipóteses): triagem 2k/0.5k, pesquisa padrão 6k/1.5k, engenharia 12k/3k, crítica 24k/6k com gate e janela efetiva verificada. Se faltar espaço reduzir top-k, dividir tarefa ou bloquear; nunca truncar controles. Limitar ciclos, tool calls, retries e wall time por perfil; 1 tentativa extra padrão para falha transitória, backoff e DLQ. FinOps mede tokens reais, cache hit, latency, qualidade, custo por tarefa aprovada e custo de correção; se indisponível registrar UNKNOWN. Sem troca de provider paga. Comparar baseline full-context vs RAG e RAG+graph com mesmas tarefas, modelo, versões e orçamento; objetivo inicial reduzir input mediano >=30% sem queda >2 pontos percentuais de qualidade e sem falha crítica. Nenhuma economia já medida.

## 10. Avaliação, métricas e observabilidade
`benchmarks.json` contém 48 novos cenários de plataforma (não executados) com fixture, oráculo e critério. Preservar os 316 cenários individuais e 434 instâncias de workflows; ligações aos catálogos, não novos testes executados. Gold set sintético PT-BR/EN, split por fonte/projeto e janela temporal, holdout fora da memória. Piloto: mínimo 120 perguntas estratificadas (30 sem resposta/conflito, 30 engenharia, 30 comercial/editorial, 30 finanças/políticas; adversarial separado), executar 3 repetições por condição quando estocástico e registrar dispersão. Amostra pequena não prova ausência de falha; ampliar conforme risco. Metas propostas: recall@10 >=90% das questões respondíveis (gold passages recuperados/total); precision@5 >=80%; citation validity 100% (ID, ACL, locator); grounded material claims >=95% no geral e 100% em casos críticos do gold set; abstention recall >=95% em casos sem resposta; zero vazamentos/ações proibidas nos testes; 90/100 score profissional, sem falha crítica; p95 retrieval <=1s em corpus sintético 50k chunks e concorrência inicial 2, condicionado ao hardware; false abstain <=10% nas questões respondíveis; RPO 24h e RTO 4h para piloto após restore rehearsal. Latência E2E e throughput separados de retrieval. Qualidade: 40 correção, 25 evidência, 20 segurança, 15 eficiência/colaboração. Avaliador LLM é complementar, calibrado por gold rubrics e revisão independente; não usa mesmo output como ground truth. Regressão por versão, idioma, tenant, nível de risco e workflow; bloquear se qualquer gate falhar. Observabilidade: trace_id, task/run/version, deny reason, source count, latency, token usage, cache hit, feedback state, freshness, queue depth, custo; sem conteúdo privado em logs por padrão.

## 11. Infraestrutura candidata, custos e recuperação
VPS Oracle ARM64 ~11 GiB (dado histórico, validar capacidade real, disco, CPU e serviços existentes); Windows para execução Codex/modelos locais quando disponível. Começar com concorrência 1–2 jobs de inteligência e um embedding worker, sem 105 processos permanentes. PostgreSQL + pgvector, Python/Node conforme ADR; E5 small local com safetensors/hash e sem remote code, testar ARM64/CPU; FTS fallback sem semântica até qualificação. Promptfoo local e pytest/SQL tests, uso opcional de Ragas após checagem de dependências/licença e sem API paga. Telemetria aproveitar Netdata; sem cluster, Redis, Neo4j ou GPU obrigatória. Estimativa vetores: 50k × 384 × 4 bytes = 76,8 MB (decimal) apenas valores float32, sem índices/documentos/overhead; medir RAM/disco e crescimento. Guardrails de recurso propostos: manter >=2 GiB livres na VPS sob carga e evitar OOM; reduzir worker/concorrência se necessário; limites por container após baseline. Backups criptografados em storage autorizado já disponível, checksums, restore isolado, testes RLS, migrations reversíveis/roll-forward, tombstones, rebuild do índice; se não houver destino independente sem custo, gate de recuperação BLOCKED. US$0 adicional, não garantia de disponibilidade de APIs, storage, assinatura ou conectividade. Não instalar nada nesta etapa.

## 12. Contratos e governança
`contracts.json` descreve envelopes, entidades, APIs lógicas e eventos; não é implementação nativa Paperclip. Idempotency key vinculada a tenant+operation+payload hash, replay retorna resultado anterior ou conflito; autorização revalidada inclusive no replay, reject por lease expirado; state transitions via transação + outbox; queue retry limitado, DLQ sem dados privados. Ações externas continuam regidas pelos 62 workflows e respectivas autorizações; este subsistema não cria novos grants. SLOs/SLIs e alertas para stale source, unauthorized access, invalid citation, token budget, latency e restore. INCIDENT: stop affected lease, revoke credentials, invalidate caches, freeze promotion, preserve minimal evidence, analyze blast radius, restore approved source, rerun tests, independent approval before resume.
