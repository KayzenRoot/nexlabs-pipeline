# NexLabs AI Enterprise — Infrastructure Architecture
**NLE-INFRA-PLAN-001 | 2026-11-26 | v0.1.0-proposed**

Status: planejamento, não instalação. NLE-INT-PLAN-001 ratificado pelo proprietário nesta conversa; conservar o conteúdo e identificadores e registrar a ratificação no futuro Decisions Ledger sem declarar promoção Git inexistente. Todos os grants permanecem negados por padrão. Nenhum novo gasto, conta, deploy, mudança em máquina, dado de cliente real ou operação financeira. US$0 incremental é uma restrição de admissão, não uma garantia de disponibilidade. O custo atual de Plus, energia, internet e infraestrutura já existente não desaparece.

## 1. Source Check e arquitetura
Consultar `source-lock.json` e `agent-runtime-bindings.json`, `workflow-runtime-bindings.json`, `skill-runtime-bindings.json`. São bindings candidatos, não configuração de API Paperclip nem grants. Source Hierarchy: checkpoint > decisões/ADRs > Scope > DoD > Architecture > Requirements > demais fontes; Git, código, testes e evidências prevalecem. Ainda não há base Git confirmada para este planejamento. Fingerprints locais protegem as entradas; Context Lock de implementação exigirá SHA base e HEAD, hashes de políticas, registry, workflow, artefatos, modelo/adapter e versões. Mudança relevante => STALE, revalidar antes de continuar.

VPS Ubuntu 24.04 ARM64 (inventário histórico: ~11 GiB RAM, 150 GB, Portainer, Netdata, sem swap), OCPUs e ocupação desconhecidos. Control plane: Paperclip autenticado, PostgreSQL externo ao processo (uma instância, databases e roles separados para Paperclip e Intelligence), pgvector no DB Intelligence, Gateway modular + dispatcher/worker persistente, 9Router opcional isolado, storage privado por tenant, monitoramento existente. Skills Registry: Git canônico + artefatos imutáveis aprovados + runtime read-only. Knowledge Graph relacional; FTS + embeddings local E5 small após benchmark; não instalar Redis, Kafka, Neo4j, Kubernetes, GPU cloud ou banco vetorial separado sem prova de necessidade.

Windows 11: execution plane para Codex CLI oficial, builds, E2E, ferramentas x64 e mídia. WSL2 Ubuntu candidato se virtualização, espaço, sandbox e recursos comprovados; preservar Codex Desktop, contas e arquivos pessoais. Worker dedicado, usuário não-admin, workspace por tenant/projeto/tarefa em disco privado, isolamento de credenciais, sem mount indiscriminado de C:, sem Docker socket. Não pressupor GPU/VRAM/RAM ou WSL instalados; verificar. VPS pode executar tarefas leves determinísticas quando desktop offline; tarefas LLM só com provider autorizado e dados elegíveis. Não alegar HA em um servidor.

Paperclip documenta Runner para Linux ARM64 com glibc >=2.39 e exceções OpenCode/Pi; Windows nativo não é presumido compatível. SSH Environments está em Experimental. Ordem: (1) pilotar local na VPS com Codex oficial, se auth e quotas legítimas; (2) qualificar SSH/WireGuard para WSL2 com autorização expressa de recurso experimental e proteção do provider pack; (3) fallback de integração via API/process adapter + worker pull privado com protocolo de lease, apenas após prova de suporte e teste de cancelamento, ou execução manual controlada no Codex Windows e entrega de evidência. Não construir bridge antes de provar lacuna. Não copiar tokens de uma máquina para outra; login oficial dedicado pelo proprietário. Sessão de assinatura pessoal não é conta de serviço nem acesso para clientes. Sem browser automation de login, extração de tokens ou bypass de sandbox. Não ativar runner que permita autoalteração das políticas ratificadas.

## 2. Conectividade e fronteiras
WireGuard autogerido candidato, VPS como hub UDP apenas porta aprovada no NSG/security list e firewall; Windows/iPhone iniciam conexão (CGNAT não exige port-forward Windows); peers e chaves distintos; AllowedIPs mínimos, revogação individual, keepalive quando necessário. Paperclip authenticated + HTTPS com trust estabelecido, acesso somente por VPN; proxy interno candidato, bind explícito; SSH com chave e sem root/password após verificação de acesso de recuperação; manter sessão administrativa de teste e rollback antes de alterar firewall. Portainer/Netdata/9Router/DB/MCP nunca publicamente expostos. Auditar exposição existente antes de mudanças. Redes Docker segmentadas: control, data, router e jobs; workers não acessam banco bruto, portas administrativas ou filesystem host. TLS quando cruzar fronteira; mTLS/token curto por worker, rotation, replay protection. Cakto e outros webhooks públicos desativados no piloto; futuro endpoint mínimo separado, assinatura oficial verificada, replay protection/rate limit, sem acesso ao admin, após gate. DNS/domínio público não necessário inicialmente. Publicação de apps de clientes é outra infraestrutura, outro escopo e autorização.

## 3. Capacidade e limites iniciais (hipóteses)
VPS: limites candidatos, MiB: Paperclip 1024; PostgreSQL 1536; Intelligence Gateway/dispatcher 512; embedding worker 768; 9Router 512; proxy/backup auxiliar 256. Total teto agregado 4608 MiB (4.5 GiB). Não é RAM garantida nem inclui SO, cache, Netdata, Portainer ou outros serviços. Desativar 9Router e embeddings se necessário. Admissão: MemAvailable >= 2048 MiB sob carga, sem OOM/pressão persistente; baseline de 24h representativo + teste isolado com serviços existentes; teto CPU de worker de embeddings 0.5 OCPU candidato, prioridade baixa, carga de DB e API prioritária. CPU total e cgroup limits medidos antes de fixar. PostgreSQL shared_buffers 256 MiB, work_mem 4 MiB, max_connections 30 inicial (ajustar conforme pools reais), sem tuning automático. Reserva de CPU/RAM para tráfego e recuperação. Swap opcional 2 GiB SOMENTE após autorização e teste de disco, não usado como capacidade de processamento. Sem upgrade automático.

Disco: orçamento de crescimento NexLabs 40 GiB candidato: imagens 10, DB/WAL 8, documentos e artefatos 8, modelos/cache 4, logs 2, staging backup 8. Requer espaço livre medido >=55 GiB para reserva de pelo menos 15 GiB; também manter >=20% livre no filesystem; se não couber, reduzir quotas, separar armazenamento já disponível ou bloquear. Não apagar volumes/imagens de outros projetos. Rotação de logs 7–14 dias (mínimo necessário e redigido), retenção de evidência conforme política. Vídeos e builds grandes no Windows; não fazer backup de caches reconstruíveis. Windows limites: começar 1 job, 1 build; WSL cap após medição, inicialmente até metade da RAM física, preservar >=4 GiB disponíveis ao host, verificar disco livre e temperatura; GPU não requerida, modelo local opcional somente após teste. Sem executar workloads não confiáveis em runner compartilhado de clientes.

## 4. Modelo de execução, quotas e custo
105 identidades lógicas; 105 heartbeats inicialmente OFF; 62 workflows disabled. Piloto: 1 slot LLM global compartilhado entre hosts, 1 tarefa determinística leve VPS (ou embedding, não ambos sob pressão), 1 job Windows total, não somar slots LLM por máquina. Um build Windows pode ocupar o slot local sem ser chamada LLM. Após benchmarks/quotas e aprovação, candidato 2 slots LLM globais, sem aumentar limite de provedor; não confundir agentes com threads. Máximo 1 run/agent, 1 mutação/repo ou recurso crítico, 1 execução externa por idempotency key. Todas as chamadas auxiliares, auditores, retries e subagentes debitam o mesmo budget central. 105 agentes não recebem 105 logins/licenças. Não compartilhar conta com terceiros.

Perfis originais: EXEC 13, ENG 27, RESEARCH 18, CREATIVE 22, QUANT 16, AUDIT 9. Roteamento em `runtime-policy.json`. Identificador exato de modelo continua null até `codex --version`, login status, listagem/seleção suportada e prova de run; consultar quota via mecanismo oficial quando disponível (ex. /status ou Usage). Priorizar Codex GPT de raciocínio alto para arquitetura/risco, esforço moderado para rotinas, sem prometer modelo específico no plano; outros providers somente se licença, termos, custo, dados, qualidade e quotas comprovados. DeepSeek 4.1 Flash é preferência candidata, não API gratuita presumida. Modelos locais somente qualificados; FTS/determinístico sem LLM como degradação legítima. Auditoria separada em identidade, workspace, contexto e revisor; HIGH_ASSURANCE exige revisão independente adequada e prova, se indisponível BLOCKED. Não degradar criticidade para poupar tokens.

9Router: projeto documenta ARM64 e combos, mas isso não prova autorização do provedor para proxy OAuth. Manter Codex oficial direto, sem repassar sessão ChatGPT a 9Router. Router OFF por padrão até SCA/licença/pinning/endpoint allowlist/telemetria/terms. Usar apenas endpoints oficiais compatíveis, com direito expresso de acesso e quota gratuita confirmada; sem pooling/rotação de contas, spoofing, fallback pago, login não oficial, cookies ou token extraction. Separar chaves por conexão, API privada, não incluir token em logs, não expor endpoint OpenAI-compatible para clientes. Router falhou => jobs aguardam; não bypass.

Budget financeiro adicional global US$0/dia/mês/projeto/run. Paperclip budget 0 pode não criar política (API só cria automaticamente se >0); enforce deny no gateway e credenciais sem faturamento/overage, além de read-back dos limites oficiais. Sem reset pago, créditos comprados, auto-recharge, billing upgrade, GPU cloud, Ads spend ou egress faturável. Provider/custo desconhecido => BLOCKED. Não assumir preço zero pelo campo `cost=0`. Reservar quota para chamadas e verificações; meta operacional de uso de até 70% da allowance conhecida, 20% para auditoria/correções, 10% margem. Se quota não legível, marcar UNKNOWN, piloto manual uma execução por vez com read-back antes e depois; nada de autoscheduling. A 70% interromper novas rotinas P2/P3, a 90% bloquear novas chamadas (incluindo retries; incidentes locais ainda executáveis), em 429/reset/cap suspender até reset comprovado. Nunca converter quota Plus em número fixo de tokens. Limite local de input/output é orçamento de contexto, não promessa de consumo total do executor; hard wall time/tool budgets quando suportados, supervisor cancela e bloqueia se adapter não garante fronteiras.

## 5. Fila e consistência
Paperclip é source of record da tarefa, dispatcher usa API documentada; fila persistente SQL própria somente para leases/eventos/admissão não oferecidos nativamente. Sem edição do DB Paperclip. Transactional outbox/inbox, idempotency `(tenant, workflow, event, step, input_hash)`, lock de recurso, fencing token monotônico por lease, transações compare-and-set, reconciliador; sem prometer exactly-once em efeitos externos. Estados: RECEIVED -> VALIDATING -> WAITING_APPROVAL/WAITING_RESOURCE/WAITING_QUOTA/READY -> LEASED -> RUNNING -> VERIFYING -> SUCCEEDED ou CORRECTION_REQUIRED/BLOCKED/DLQ/CANCELLED/UNKNOWN_EFFECT. Sem avançar dependência não concluída. Lease 120s renovável a 30s candidato, wall time por perfil, timeout não prova que processo parou. Revogar lease e cancelar; antes de reatribuir job, confirmar término/fencing no destino; UNKNOWN_EFFECT exige read-back e humano, sem retry cego. Um retry para falha transitória interna idempotente com backoff/jitter 30–120s; 429 segue Retry-After/reset. Dead letter sem payload privado e com ponteiro ACL. Revalidar policy/Context Lock no dequeue, tool call, completion, aprovação e replay. Evento atrasado/duplicado não cria publicação, compra, PR merge ou venda duplicada.

Prioridades: P0 incidentes, revogações, backup/restore, contenção; P1 correções, auditorias, clientes com compromisso autorizado; P2 receita e entregas necessárias; P3 pesquisa, marketing em draft, exploração. Aging e round-robin por tenant; nenhum projeto toma todos os slots; P0 pode pausar/cancelar com segurança, não interromper operação irreversível. Teto inicial 100 jobs pendentes global, 20 por projeto, 2 novos jobs por run de orquestrador, profundidade 3 de delegação, após exceder bloquear/compactar rotinas não críticas, não descartar tarefa aceita. Rotinas desativadas; agrupar eventos e debouncing, no máximo 1 execução por janela, skip/coalesce se ainda rodando. Horários em America/Sao_Paulo, dados UTC. Dashboard de motivos WAITING, não esconder dependências. Throughput = min(capacidade slots×tempo disponível/tempo médio, quota efetiva, recursos e aprovação); não prometer 24/7 LLM.

## 6. Segurança HIGH_ASSURANCE
Roles: proprietário/admin humano; ZEUS delega, não concede; PLUTUS mede e bloqueia orçamento, não gasta; ARGUS revisa/bloqueia e escala; ATLAS opera runbooks limitados; HEPHAESTUS implementa em branch; auditor não aprova o próprio trabalho. Gateway enforcement fora de prompt; grant = interseção agent/task/tenant/skill/host/provider/risk/policy. Sem grants por hierarquia ou por RAG. Clientes segregados em storage, DB RLS (não owner, FORCE onde aplicável), workspaces, caches, embeddings, sessions, logs e tool credentials; role DB somente gateway. Dados de clientes para provedor hospedado só com termos, retenção, transferência e finalidade autorizados, controles de treinamento verificados; senão sanitização aprovada, local qualificado ou BLOCKED. Sem chaves privadas, trading real, carteiras, compras, campanhas pagas ou mainnet. Não enviar dados reais no piloto. Artefatos/skills/policies read-only, signed/hash-pinned, no auto-sync, sem editar AGENTS/SOUL/TOOLS críticos, sem liberar privilégios. `sudo`, admin, Docker socket, host mounts, secrets store raw e shell de produção proibidos. Egress allowlist, SSRF/DNS rebinding protections, no unrestricted MCP; ferramenta valida argumentos e outputs, aprovação vinculada a hash/escopo/expiração. GitHub App/token fino por repo, curta duração quando suportado; PR/CI sem secrets para conteúdo não confiável; protected main, sem força/bypass. Não armazenar tokens Plus/9Router em Git, Docker image, logs ou backup comum. Secret envelope/recovery separado com acesso humano; rotate/revoke, não restaurar sessão revogada. Supply chain: versões/digests, SBOM, SCA, SAST, licença, ARM64 manifest, health checks; atualizar via PR canary/rollback. Sem instalação automática de fontes candidatas.

## 7. Backups e recuperação
Postgres: dump consistente por database + globals necessários (roles/ownership, protegidos), arquivos, manifests, outbox/ledger e version locks; coordenar snapshot DB/storage por quiesce/epoch para consistência. Criptografia autenticada, manifest SHA256 e versão do runtime; restic ou alternativa auditada candidata, cópia VPS staging + destino independente Windows/HD externo existente criptografado e autorizado, verificar espaço e disponibilidade; OCI Object Storage opcional somente quota/billing verificados, não único destino da mesma tenancy. Não presumir HD disponível nem formatá-lo. Segredos/chaves recovery separados, sem OAuth tokens persistidos em backups comuns. Daily 1, retenção inicial 7 diários e 4 semanais condicionada à capacidade; testar recuperação de 1 arquivo semanal, restore completo mensal e antes de migration/upgrade. RPO 24h, RTO 4h piloto para perda recuperável no ambiente de reposição existente, medidos; não garantidos em reclaim/sem máquina substituta. Se destino offline ou última cópia >24h, alerta e parar ingestão nova sensível/produção até ressincronizar. Sem restore de dados revogados: aplicar tombstones, ACL, token rotation e policy epoch antes de abrir rede. Restaurar isolado, conferir hashes/roles/RLS/skills, consistência DB+storage, reindexar, replay idempotente, comparar counts e KPIs, canary, auditoria e aprovação humana. Não iniciar external effects automaticamente após restore. Ransomware: cópia offline/imutável se disponível, não deixar todos os backups graváveis pelo mesmo usuário. Oracle pode recuperar VPS ociosa; não gerar carga artificial; runbook recriar em infraestrutura autorizada, se não houver reposição, BLOCKED. Single VPS é SPOF, sem SLA de HA.

## 8. Observabilidade e SLOs candidatos
Netdata existente + métricas estruturadas leves, logs redigidos com trace_id, run_id, tenant opaco, host, model/adapter e versões, quota freshness, queue age/depth, tokens medidos/UNKNOWN, erros, deny reason, backup age, disk/RAM, RLS denies, latency. Prometheus/Grafana só se gap comprovado. Alertas internos críticos em memória/queue; canal externo só após autorização. CPU >80% sustentado 5min => parar novos jobs pesados; MemAvailable <2 GiB => pausar admissão de jobs, <1 GiB/OOM => contenção; disco <20% livre => pausar ingestão/build e revisar; backup age >24h => gate; worker heartbeat expirado => offline e reconcile. SLO piloto: P95 retrieval <=1s/50k chunks/2 concorrentes conforme INT; API P95 <=500ms para endpoint leve sob carga piloto, sem incluir LLM; zero efeitos duplicados, zero vazamentos e zero gasto não autorizado nos testes; restore RPO/RTO acima. Métricas benchmarkadas e não declaradas atingidas. Registrar latência total separada do tempo de fila. Testar saturação, reboot, desconexão Windows, 429, DB restart, filesystem cheio, perda de lease, crash durante commit, restauração, versão stale, rollback, credentials revoked.

## 9. Preflight somente leitura
VPS: `uname -m; cat /etc/os-release; lscpu; free -h; swapon --show; df -hT; lsblk; docker version; docker compose version; docker ps; docker stats --no-stream; ss -lntup; uptime`; não capturar env, secret ou logs privados. Verificar cgroup, glibc, imagens multiarch por manifest/digest, espaço/inodes, Portainer/Netdata, firewall OCI e host, plan/quotas/billing via console read-back. Não mudar shape, volume, conta ou ports sem gate. Windows: Get-CimInstance Win32_ComputerSystem/Win32_Processor/Win32_VideoController; Get-Volume; wsl --status; wsl --list --verbose; codex --version; codex login status (se suportado, sem token); git --version; Docker/virtualização e status de energia. Confirmar PC ligado, usuário dedicado e backup disponível. GitHub: repo/branch, Actions quota e limite de gastos; contas privadas podem cobrar após franquia; sem tornar código privado público para economizar. Qualificar ferramentas externas em sandbox, fixtures sintéticas, sem autorizar live. Se dado faltar, bloquear gate específico; não adivinhar.
